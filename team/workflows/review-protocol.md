# レビュープロトコル — 内部レビュー → 玉城先生審査 → 承認

---

## レビューフロー

```
りゅうき（実装完了）
    ↓
けいじ（内部レビュー）
    ↓ 問題なし
玉城先生（第三者審査）
    ↓ 承認
りつい（PR マージ承認）
    ↓
develop ブランチへマージ
```

---

## Step 1: 内部レビュー（けいじ）

**トリガー:** りゅうき から「実装完了・レビュー依頼」の通知

**チェックリスト:**
- [ ] ロジックの正確性
- [ ] セキュリティ（OWASP Top 10）
- [ ] エラーハンドリング
- [ ] 命名規則・コーディング規約
- [ ] テストの有無と品質
- [ ] パフォーマンス上の懸念

**判定:**
- 承認 → 玉城先生へ
- 修正依頼 → りゅうき に差し戻し（軽微な問題）

---

## Step 2: 第三者審査（玉城先生）

**トリガー:** けいじ の内部レビュー承認後

**審査内容:**
- けいじ が見落とした点の確認
- 設計・アーキテクチャレベルの評価
- 仕様との整合性確認
- 総合的な品質判定

**判定区分:**

| 判定 | 条件 | 次のアクション |
|------|------|--------------|
| 承認 | 全項目問題なし | りつい による PR マージへ |
| 条件付き承認 | 軽微な修正要 | 修正後 確認なしで続行 |
| 差し戻し | 重大な問題あり | りゅうき が修正 → 再度 Step 1 から |

---

## Step 3: PR マージ承認（りつい）

**トリガー:** 玉城先生の承認

**アクション:**
```bash
# りつい が実行（Bash 権限）
git checkout develop
git merge --no-ff feature/[issue-id]-[description]
git push origin develop
```

**注意:** develop → main のマージは**ユーザー承認必須**

---

## 差し戻し時のサイクル

```
玉城先生（差し戻し）
    ↓ 具体的な改善指示
りゅうき（修正実装）
    ↓
けいじ（再レビュー）
    ↓
玉城先生（再審査）
```

差し戻しは**何度でも発動する**。品質基準を満たすまでサイクルを繰り返す。

---

## CHANGELOG 記録

レビュー完了時に以下をログに追記:
```
YYYY-MM-DD | [けいじ] review: [機能名] レビュー完了 — [承認/差し戻し]
YYYY-MM-DD | [玉城先生] review: [機能名] 第三者審査 — [承認/差し戻し/条件付き承認]
YYYY-MM-DD | [りつい] feat: [機能名] develop へマージ
```
