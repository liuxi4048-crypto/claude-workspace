## 2. セキュリティ設計

### 2-1. セキュリティ基本方針（CISO管轄）

```
原則1: 最小権限の原則
  → 各メンバーは自分の役割に必要な情報のみにアクセスする

原則2: 多層防御（Defense in Depth）
  → 単一の防御に頼らず、複数層でリスクを軽減する

原則3: ゼロトラスト
  → 内部・外部を問わず、常に検証してから信頼する

原則4: セキュリティbyデザイン
  → 機能追加時に後付けでなく設計段階からセキュリティを組み込む
```

### 2-2. セキュリティ責任マトリクス

| 領域 | 主担当 | 副担当 | 承認者 |
|---|---|---|---|
| 情報セキュリティポリシー | CISO | CLO | Chairman |
| APIキー・認証情報管理 | CISO | CTO | COO |
| コードセキュリティ | CTO | CISO | Internal Tech Auditor |
| クライアントデータ保護 | CISO | CLO | COO |
| AIモデルセキュリティ | CAIO | CISO | CISO |
| 契約・法務リスク | CLO | CISO | Chairman |
| 財務セキュリティ | CFO | Internal Auditor | Chairman |

### 2-3. 技術セキュリティ要件（CTO+CISO必読）

#### API・認証情報
```
必須要件:
□ APIキーは環境変数（.env）で管理。コードにハードコードしない
□ .env ファイルは .gitignore に必ず追加
□ GitHub Secretsを使用（Actions経由でのみアクセス）
□ APIキーは90日ごとにローテーション
□ 本番・開発・テスト環境でAPIキーを分離する

禁止事項:
× APIキーをチャット・メール・ドキュメントに記載しない
× 共有アカウントの使用
× 期限切れAPIキーの放置
```

#### コードセキュリティ
```
必須要件:
□ 入力値の検証・サニタイズ（SQLインジェクション・XSS対策）
□ 依存パッケージの脆弱性スキャン（npm audit / snyk）
□ HTTPSのみ使用（HTTP禁止）
□ CORS設定を最小限に絞る
□ レート制限の実装（API endpoint）
□ エラーメッセージに内部情報を含めない

スプリント末チェック（Internal Tech Auditor）:
□ 新規依存パッケージの脆弱性確認
□ ハードコードされた認証情報がないか確認
□ SQLインジェクション・XSSのリスク確認
```

#### インフラセキュリティ
```
Vercel（本番環境）:
□ 環境変数はVercel Dashboardで管理
□ Preview デプロイへの不正アクセス防止
□ カスタムドメインのSSL証明書確認

Supabase（DB）:
□ Row Level Security（RLS）を必ず有効化
□ DBへの直接アクセスは開発時のみ
□ バックアップを週次で確認
```

## 3. 情報管理・機密区分

### 3-1. 情報分類レベル

| レベル | 分類 | 例 | 取扱いルール |
|---|---|---|---|
| **L1** | 極秘 | APIキー・パスワード・クライアント個人情報 | 暗号化必須・共有禁止 |
| **L2** | 機密 | 契約書・見積書・財務情報・ソースコード（非公開） | 関係者のみ・ログ記録 |
| **L3** | 社内限定 | 日報・決定ログ・設計書・提案文（下書き） | チーム内のみ |
| **L4** | 公開可 | README・公開ドキュメント・採用情報 | 制限なし |

### 3-2. ファイル管理ルール

```
C:\Claude\team\          → L3（社内限定）
C:\Claude\aiship\        → L2（機密）
C:\Claude\aiship\sales\  → L2（機密）
.env ファイル            → L1（極秘）・Gitに含めない
APIキー関連ファイル      → L1（極秘）
```

### 3-3. クライアント情報管理（CLO+CISO）

```
収集する情報:
  ・会社名・担当者名・連絡先（L2）
  ・案件内容・要件（L2）
  ・契約金額（L2）

禁止:
  × 個人情報をクラウドストレージに無断保存
  × 第三者への無断開示
  × 契約終了後5年以上の不要な保持
```

```

```

  □ 新規導入パッケージのライセンス確認
  □ CLOへ不明点をエスカレーション

## 6. AIガバナンス

### 6-1. AIガバナンス原則（CAIO+CLO+CISO三者合議）

```
原則1: 透明性
  AI生成物であることを適切に開示する

原則2: 公平性
  AIが差別的・偏向的な出力をしないよう監視する

原則3: 説明可能性
  AIの判断根拠を説明できる設計にする

原則4: 人間による監督
  重要判断はAIのみに委ねず、オーナーが最終確認する

原則5: プライバシー保護
  個人情報をAIに学習・記憶させない
```

### 6-2. AI機能設計ゲート

`AI設計` トリガー発動時、CAIO+CLO+CISOが以下を評価する。

```
【AIガバナンス審査チェックリスト】

CAIO視点:
  □ 使用するモデル・APIの選定根拠が明確か
  □ データの品質・バイアスリスクを評価したか
  □ 出力の精度・信頼性を測定する手段があるか
  □ コスト見積もりは妥当か（CFOと連携）

CLO視点:
  □ 著作権侵害リスクはないか（生成コンテンツ）
  □ 個人情報をAIに入力しないよう設計されているか
  □ AI Act等の規制リスクを評価したか
  □ 利用規約（Claude API Terms等）に準拠しているか

CISO視点:
  □ プロンプトインジェクション対策はあるか
  □ APIキー・認証情報の保護は適切か
  □ AI出力の検証・フィルタリングはあるか
  □ ログ・監査証跡は残るか

→ 三者全員の承認でCTOへ実装指示
→ 1名でも否定なら再設計
```

### 6-3. AI出力品質基準

```
クライアントへの納品物にAI生成物を使用する場合:
  □ 人間（CTO/CPO）によるレビュー必須
  □ ファクトチェック実施
  □ AI生成である旨をクライアントへ開示（契約書に記載）
  □ 著作権関連リスクをCLOが確認
```

## 7. インシデント対応

### 7-1. インシデント分類

| 分類 | 例 | 初期対応時間 |
|---|---|---|
| **P0（緊急）** | APIキー漏洩・本番障害・個人情報漏洩 | 即座（30分以内） |
| **P1（重大）** | セキュリティ脆弱性発見・契約トラブル | 4時間以内 |
| **P2（中）** | バグによる機能停止・納期リスク | 24時間以内 |
| **P3（軽微）** | 軽微なバグ・UI崩れ | 次スプリント内 |

### 7-2. P0インシデント対応フロー

```
インシデント発生
        ↓
発見者が即座に COO へ報告
        ↓
COO: インシデント分類・CISO+CLO召喚
        ↓
CISO: 被害範囲の特定・封じ込め
CLO: 法的報告義務の確認（個人情報漏洩なら72時間以内に報告義務）
        ↓
COO: Chairman へエスカレーション
        ↓
Chairman: 対外対応方針の決定
        ↓
COO: 対応実行・進捗管理
        ↓
CISO: 根本原因分析（ポストモーテム）
        ↓
Internal Auditor: 再発防止策の監査
```

### 7-3. APIキー漏洩時の緊急対応

```
即座に実行:
  1. 漏洩したAPIキーを即座に無効化（各サービスのダッシュボード）
  2. 新しいAPIキーを発行
  3. 環境変数・GitHub Secretsを更新
  4. 漏洩経路の特定（gitログ確認等）
  5. CISOがポストモーテムを作成
  6. 再発防止策をpunch_list.mdに登録
```

| データ種別 | 保存場所 | 暗号化 | 保存期間 |

### 8-2. バックアップ方針

```
コード（GitHub）:
  → GitHubがバックアップ。ローカルクローンも維持

チームファイル（C:\Claude\team\）:
  → 週次でGitHubにpush（自動commit hookで対応済み）
  → 月次でローカルバックアップ

クライアントデータ:
  → 暗号化した上でローカル + クラウドストレージ（Dropbox等）
```

## 10. 監査体制

### 10-1. 監査カレンダー

| タイミング | 監査種別 | 実施者 | 報告先 |
|---|---|---|---|
| スプリント末（毎週/隔週） | 技術プロセス監査 | Internal Tech Auditor | Internal Auditor |
| スプリント末 | 全体・財務監査 | Internal Auditor | Chairman + オーナー |

### 10-2. 監査の独立性確保

```
Internal Auditor:
  → COO・CEOの指揮下に入らない
  → オーナーに直属
  → 指摘はpunch_list.mdに必ず記録

External Auditor:
  → 成果物のみを評価（内部プロセス不参照）
  → レポートはオーナーのみに提出
  → COO・CEOには非共有
```

## 13. 緊急連絡・エスカレーション

### エスカレーションパス

```
軽微な問題（🟢）
    └─ 担当CxO → COO（日報で報告）

中程度の問題（🟡）
    └─ 担当CxO → COO（即時報告）→ 対処計画

重大な問題（🔴）
    └─ 発見者 → COO（即時）→ CISO/CLO（即時）→ Chairman → オーナー

緊急インシデント（P0）
    └─ 発見者 → COO + CISO（同時・即時）→ 30分以内にChairman判断
```

### 判断が必要な時の最終権限者

| 状況 | 最終権限 |
|---|---|
| 通常業務判断 | COO |
