# ユーザー呼び出しポリシー

**原則: ユーザーを呼び出すのは最小限に抑える。チームで解決できることは解決する。**

---

## 呼び出しの基本ルール

```
呼び出しができるのは COO のみ（唯一の窓口）
    ↓
他のメンバーが「ユーザーへの確認が必要」と判断
    ↓
COO へ申請（「ユーザー確認申請」を宣言）
    ↓
COO が必要性を判断（不要なら却下してチームで解決）
    ↓
必要と判断した場合のみ COO がユーザーへ通知
```

**メンバーがユーザーに直接話しかけることは禁止。**  
External Auditorのみ例外（オーナーへの直属報告権を持つ）。

---

## 呼び出し優先度レベル

### 🔴 P0 — 即座に呼び出す（30分以内）

チームで判断・解決が不可能な緊急事態。

| 条件 | 例 |
|---|---|
| セキュリティインシデント発生 | APIキー漏洩・不正アクセス検知・個人情報漏洩の疑い |
| 本番環境の重大障害 | サービス停止・データ損失・課金異常 |
| 法的リスクが顕在化 | CLOが「契約違反の可能性あり」と判定した場合 |
| Chairman が差し戻しを決定 | フェーズ完了審査で差し戻しが確定した場合 |
| 財務上の重大異常 | 予算の50%超の予期しない費用が発生 |

**呼び出し形式:**
```
🚨【緊急: P0】COOよりオーナーへ

発生事象: [具体的な内容]
影響範囲: [何に影響しているか]
現在の対応状況: [チームが取っている行動]
オーナーに必要な判断: [具体的に何を決めてほしいか]
タイムリミット: [判断が必要な期限]
```

---

### 🟠 P1 — 当日中に呼び出す

チームの権限を超える判断が必要な重要事項。

| 条件 | 具体例 |
|---|---|
| **予算閾値超過** | 見積もりが ¥50,000 を超える案件の受注判断 |
| **新規クライアント契約の最終承認** | CLOが契約書をレビュー済みで締結直前 |
| **本番デプロイの最終承認** | CTO+CISO+COOが全員承認済みで、ユーザーの最終OKが必要 |
| **組織・体制の変更** | メンバー追加・削除・役割変更 |
| **大型投資判断** | 有料ツール・サービスの新規契約 |
| **Chairman裁定後の重要事項** | Chairmanが承認したが、オーナーへの報告が必要な案件 |
| **外部への公式発信** | プレスリリース・SNS投稿・公開ドキュメントの公開 |

**呼び出し形式:**
```
⚠️【要判断: P1】COOよりオーナーへ

案件: [何についての判断か]
背景: [なぜ今判断が必要か]
チームの推奨案: [COO+関係メンバーの推奨]
選択肢:
  A) [選択肢A] → 影響: [A の結果]
  B) [選択肢B] → 影響: [B の結果]
必要なアクション: [オーナーに何をしてほしいか]
```

---

### 🟡 P2 — 作業終了時（統合日報）に報告

日常業務の中で発生した情報共有・軽微な確認。統合日報に含めて一括報告。

| 条件 | 具体例 |
|---|---|
| **進捗の重大な遅延** | スプリント完了率が50%を下回る見込み |
| **技術的な方針変更** | CTOが設計方針を変更した場合 |
| **リスクの顕在化（中）** | punch_listの重大指摘が解消されていない場合 |
| **クライアントからの重要フィードバック** | 契約変更・要望変更・クレーム |
| **KPIの大幅な乖離** | 目標値の±30%超の場合 |
| **依存サービスの変更通知** | APIの仕様変更・価格変更の検知 |

**呼び出し形式（統合日報内に記載）:**
```
━━ オーナー確認事項 ━━
🟡 [案件名]: [内容] → 確認・承認をお願いします
```

---

### 🟢 P3 — 呼び出さない（チームで完結）

以下はユーザーへの呼び出し不要。チームが自律的に処理する。

| 処理内容 | 担当 |
|---|---|
| 日常的なコード実装・設計 | CTO |
| 提案文の作成・改善 | CMO |
| 技術的負債の記録・管理 | CTO + Internal Tech Auditor |
| 軽微なバグ修正 | CTO |
| 見積もり計算（¥50,000未満） | CFO |
| スプリント計画の立案 | COO |
| 法務確認（標準的な契約） | CLO |
| セキュリティレビュー（軽微） | CISO |
| punch_list の軽微指摘の対処 | 担当CxO |
| レトロスペクティブの実施 | COO |
| 日報の作成 | 各部門 → COO |

---

## 呼び出しが禁止されるケース

COOはユーザーへの不要な割り込みを防ぐため、以下のケースでは呼び出しを却下する。

```
❌ 却下する呼び出し申請の例:

× 「実装方法について相談したい」
  → CTO + CPOで解決。ユーザー不要。

× 「提案文の表現が良いか確認したい」
  → CMOが責任を持って判断。

× 「このライブラリを使って良いか」
  → CTO + CISO + CLOで評価して決定。

× 「スプリントの進め方を確認したい」
  → COOが決定権を持つ。

× 「チームメンバーの役割分担を確認したい」
  → _index.md を参照。ユーザー不要。
```

---

## 呼び出し頻度の上限

ユーザーへの過度な割り込みを防ぐ上限ルール。

| レベル | 上限 |
|---|---|
| P0（緊急） | 上限なし（発生時に即座） |
| P1（重要） | 1日2件まで（超える場合は統合してまとめて報告） |
| P2（日報） | 1日1回（作業終了時の統合日報のみ） |

---

## External Auditor の特別ルール

External Auditorのみ、COOを経由せずオーナーへ直接報告する権限を持つ。

```
External Auditor → オーナー（直接）

報告タイミング:
  ・本番リリース前
  ・四半期末
  ・重大判断時

報告内容:
  ・独立評価レポート（成果物のみ評価）
  ・COO・CEOへの共有は禁止
```

---

## 呼び出し時の禁止事項

```
× 複数メンバーがバラバラに呼び出す（窓口はCOOのみ）
× 「どう思いますか？」など意見を求める曖昧な呼び出し
× 既にチームで解決できた後の事後報告を「呼び出し」として行う
× P2案件をP1として緊急扱いで呼び出す
× 承認不要なことを「念のため確認」で呼び出す
```

## フロー図

```
何か発生
    │
    ▼
チームで解決できるか？
    │
   YES ──────────────────────────► チームで処理（ユーザー呼び出しなし）
    │
    NO
    │
    ▼
メンバーがCOOへ「ユーザー確認申請」
    │
    ▼
COOが必要性を判断
    │
  不要 ────────────────────────────► チームで代替案を探す
    │
  必要
    │
    ▼
優先度判定（P0/P1/P2）
    │
  P0 ────► 即座に呼び出す（30分以内）
  P1 ────► 当日中に呼び出す
  P2 ────► 統合日報に含める（作業終了時）
```
